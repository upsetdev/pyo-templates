# Adding a template

Templates run on other people's servers, next to their data, so the rules here
are strict on purpose.

A template is `templates/<id>/compose.yaml`: a valid Docker Compose file, with
what Pyo needs to know in `x-pyo` fields. Compose ignores `x-` fields, so the
same file runs with `docker compose up`.

## Steps

1. Make `templates/<id>/`. `<id>` is lowercase with dashes, and it can't change
   later.
2. Start from the project's own compose file (its docs or repository), and cut
   it down to the [supported subset](#supported-compose) below. Keep the
   upstream images, variables and settings. Don't copy other platforms'
   templates.
3. Add the `x-pyo` fields (see the [reference](#x-pyo-reference)). Your editor
   gets completion from `schema.json`.
4. Set `tier: community` and `author` to your GitHub username.
5. Write each image as `registry/repository:tag` and run `bun run pin`: it adds
   `@sha256:…` from the registry.
6. Add `logo.svg` if the project has one you may use (optional).
7. Run `bun install && bun run validate`, try it locally (see
   [below](#testing-locally)), then open a pull request.

## From an upstream compose file

Most upstream files need the same few changes:

| Upstream                                  | In a template                                                                    |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| `image: postgres:17`                      | A full name, pinned: `docker.io/library/postgres:17@sha256:…`                    |
| `ports: ["8080:8080"]`                    | `expose: ["8080"]`, and how Pyo exposes it in `x-pyo.expose`                     |
| `./data:/data` (a host path)              | A named volume, `data:/data`, sized in `volumes.data.x-pyo.sizeGi`               |
| `env_file`, `KEY=value` lists             | `environment:` as `KEY: value`                                                   |
| `SECRET=change-me`                        | `SECRET:` with no value, and `SECRET` in `x-pyo.generate`                        |
| A database service (`postgres`, `mysql`)  | `x-pyo.database`, and keep the service for local tests with `profiles: [local]`  |
| `command: sh -c "…"` (a string)           | A list: `command: [sh, -c, "…"]`                                                 |
| `${VAR}` interpolation                    | A plain value, with `$$` for a literal `$`                                       |
| `depends_on` a database                   | `restart: unless-stopped` (it waits by retrying)                                 |
| Config files mounted from the host        | Variables or flags, or files the `entrypoint` writes before it starts            |

## Supported Compose

Top level: `services`, `volumes` and `x-pyo`. In a service:

- `image`: with its registry, tag and digest, from a public registry
  (docker.io, ghcr.io, quay.io, registry.k8s.io, registry.gitlab.com,
  mcr.microsoft.com, public.ecr.aws, data.forgejo.org). No `latest`.
- `command` and `entrypoint`: lists, run without a shell. `{{key}}` in
  `command` takes a deploy-form field's value.
- `environment`: `KEY: value`. A key with no value is a secret: generated by
  Pyo (`x-pyo.generate`) or typed in the deploy form (a sensitive field).
- `volumes`: one named volume per service (`data:/path`).
- `expose`: the container's ports (`"53/udp"` for UDP).
- `healthcheck`: required. Pyo's own probe in `x-pyo` (`http` or `tcp`), a
  `test` command, or `disable: true`. `start_period` and `interval` are Pyo's
  initial delay and period.
- `deploy.replicas` and `deploy.resources`: `reservations` are what Pyo
  requests, `limits` the most it may use (`cpus: "0.25"`, `memory: 256M`).
- `depends_on`, `restart` (for `docker compose` only), and `profiles: [local]`.
- `x-pyo` (below).

**Refused, with a reason:** `build`, `privileged`, `network_mode`, `devices`,
`cap_add`, host bind mounts, published `ports`, `extends`, `env_file`,
`volumes_from`, `pid`, `ipc`, `security_opt`, `sysctls`, `links`, `extra_hosts`,
`configs`, `secrets`, top-level `networks` and `include`, and any key not listed
here.

**Several services:** the one Pyo deploys is named like the folder. Others are
either `profiles: [local]` (only for `docker compose`, for example a database to
test with, which Pyo ignores), or companions Pyo deploys next to it, like
Plausible's ClickHouse. A companion's variables have values (no secrets), and
the main service reaches it by its name, as in Compose:
`http://plausible-events:8123` works locally and on Pyo. A deployed service
can't `depends_on` a local one: `docker compose config` would fail without
`--profile local`.

## x-pyo reference

```yaml
x-pyo:                        # the template
  name: Umami                 # 2–40 characters
  description: Simple, privacy-focused website analytics…   # 20–160
  category: monitoring        # databases, caches, storage, networking, monitoring,
                              # messaging, developer-tools, web, ai, other
  logo: logo.svg              # optional, next to compose.yaml
  tier: community             # official is for the Pyo team
  author: your-github-name
  homepage: https://umami.is  # the project's website
  version: 1.0.0              # the template's own version (semver), see Versions
  appVersion: "3.4.1"         # optional: the app's version the default tag runs
  minPyoVersion: 0.1.0
  kind: application           # application: people open it. service: other services use it
  featured: true              # maintainers only: shown first
  hidden: true                # maintainers only: left out of galleries
  versions:                   # more versions in the deploy form. The image's tag is the default
    - { tag: "7.0", digest: "" }    # bun run pin fills it in
  generate:                   # secrets Pyo makes once, when deploying
    - APP_SECRET              # 24 letters and digits
    - { key: LONG_KEY, format: long }               # 64 letters and digits
    - { key: HEX_KEY, format: hex-32 }              # 32 random bytes as hex
    - { key: APP_KEY, format: base64-32, prefix: "base64:" }
  database:                   # or databases: [ … ] for several, one per engine
    engine: postgres          # mysql, postgres or kv
    extensions: [pg_trgm]     # optional: what the app needs (Postgres or KV)
    env:                      # the app's variable: the database's
      DATABASE_URL: DATABASE_URL_DIRECT
  fields:                     # the deploy form (the version picker is automatic)
    - { key: admin, label: Admin user, type: text, default: admin, required: true, envKey: ADMIN_USER }
  hints:                      # short notes shown when deploying
    - Sign in as admin, then change the password.

services:
  umami:
    x-pyo:                    # the service
      workload: StatefulSet   # default: StatefulSet with a volume, Deployment without
      expose:                 # each port in expose:, by name
        - { name: http, port: 3000, as: http }    # http: a web port that can get a domain
        - { name: api, port: 6334, as: internal } # internal (default): inside the cluster only
        - { name: dns, port: 53, as: tcp, protocol: udp }   # tcp: a public TCP/UDP port
      gpu: { use: optional, count: 1 }   # NVIDIA GPUs: optional or required
    healthcheck:
      start_period: 30s
      interval: 10s
      x-pyo: { http: { path: /api/heartbeat, port: 3000 } }   # or { tcp: 3000 }

volumes:
  data:
    x-pyo: { sizeGi: 10, required: true }   # required: false lets people skip it
```

### Versions

`version` is the template's own version, separate from the app's. Pyo
records it with every service deployed from the template, so bump it on every
change to `compose.yaml`: **patch** for an image bump, **minor** for a new
option (a field, a variable), **major** for a change that needs people to act
(a data migration, a renamed variable). A new template starts at `1.0.0`.

`appVersion` is the app's version the default image tag runs, as people know
it (`0.107.55` for `v0.107.55`). Leave it out when the tag doesn't say
(`sha-4bfc5bb`). `upgrade` (`breaking`, `upgradeFrom`, `notes`) is reserved
for upgrades. Pyo doesn't read it yet.

### Databases

`database` (or `databases`, one per engine) asks for a database: when
deploying, people pick one of their team's or make one, and Pyo connects it.
Each key in `env` becomes one of the service's variables, set from one of the
database's, or several joined by `:` (`MYSQL_HOST:MYSQL_PORT` is host:port):

- **mysql:** `DATABASE_URL`, `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`,
  `MYSQL_PASSWORD`, `MYSQL_DATABASE`.
- **postgres:** `DATABASE_URL` (through the connection pooler, in transaction
  mode, when it's on), `DATABASE_URL_DIRECT` (straight to the primary), and
  the parts `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`,
  `POSTGRES_PASSWORD`, `POSTGRES_DATABASE` (also the primary). Use the direct
  ones for apps that run migrations or use prepared statements, advisory locks
  or other session features (Prisma, Ecto, most ORMs). If unsure, go direct.
- **kv:** `REDIS_URL`, and `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`. It
  speaks the Redis protocol through a proxy that follows failover. It refuses
  `MONITOR`, `CLIENT TRACKING` (and other `CLIENT` subcommands) and admin
  commands like `CONFIG`.

`extensions` lists the extensions the app needs, by name from Pyo's catalog
(`scripts/extensions.ts`, a copy of Pyo's): Postgres extensions, or KV
modules (`valkey-json`, `valkey-bloom`, `valkey-search`). Pyo turns on the
ones it manages (`vector`, `pg_cron`, …) with a new database. For an existing
one, the deploy form asks to turn on the missing ones. The other Postgres
ones (`pg_trgm`, `citext`, `pgcrypto`, …) the app's own role creates with
`CREATE EXTENSION`, so list them only when the app does that itself. Add one
only when the project's docs or migrations need it.

These variables aren't otherwise set in `environment`, except with a value for
local testing (pointing at a `profiles: [local]` database): Pyo drops those and
sets them from the database.

### References

A value can use `$${{self.PUBLIC_URL}}` (`$$` is a literal `$` in Compose) and
the service's other values: `HOST`, `PORT`, `URL`, `PUBLIC_DOMAIN`. `PUBLIC_*`
needs a domain, so the deploy form asks for one.

## Rules

CI enforces these:

- **Data only.** Nothing outside the subset above: no builds, privileged
  containers, host paths or raw Kubernetes objects.
- **Pin every image** by digest, from a public registry. No `latest`.
- **Bump `version`** whenever `compose.yaml` changes.
- **No secrets in the file.** A secret has no value and is generated or comes
  from a sensitive field.
- **A health check and resources** are required, and a reservation can't
  exceed its limit.
- **Stateful services** (with a volume) run one replica.
- **GPUs:** templates that use them keep their models on a volume.
- **Plain logos:** drawing elements only, under 16 KB, with no scripts, links or
  external references.
- **Your own templates:** only the author or a maintainer changes a template.
  Only maintainers set `featured` or `hidden`, and change `catalog.yaml`,
  `schema.json`, `template.schema.json`, `scripts/` and `.github/`.

## Testing locally

```bash
docker compose -f templates/<id>/compose.yaml config        # valid Compose?
docker compose -f templates/<id>/compose.yaml --profile local up -d
docker compose -f templates/<id>/compose.yaml --profile local down -v
```

Secrets with no value come from your shell, so set them first
(`APP_SECRET=x docker compose … up`). Ports aren't published, so reach the app
from its network:

```bash
docker run --rm --network <project>_default curlimages/curl -s http://<service>:<port>/
```

Compose doesn't fill in `$${{self.…}}` values. To try an app that needs its own
address, override them in a file you don't commit:

```yaml
# local.yaml, then: docker compose -f templates/<id>/compose.yaml -f local.yaml up
services:
  <id>:
    environment:
      BASE_URL: http://localhost:8000
```

## Review

A maintainer also checks what CI can't:

- The image comes from the project itself, or a publisher you'd trust.
- It runs as described, and starts with the defaults.
- It isn't exposed publicly unless it's meant to be.

A `community` template is reviewed, but it isn't maintained by the Pyo team.
Pyo admins choose whether to show them.
